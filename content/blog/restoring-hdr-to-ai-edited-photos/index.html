I sometimes use the latest AI image-editing tools to touch up photos and remove objects. The problem is that the current tools I have tried, including the OpenAI and Gemini image-editing paths, return an image with the HDR layer missing. That is the pop you see in the brightness of the sky in an iPhone photo: a layer called the gain map.

Picture formats have changed over the years. We still see a box of pixels on the screen, but more information is being stored alongside those pixels. One practical way to make HDR images work across old and new devices is to keep an ordinary SDR image and attach extra information that HDR-capable software can use. A gain map is that extra information: a second image that tells a compatible display how much brighter to render each part of the base image.

The Google Ultra HDR specification describes this as a conventional low-dynamic-range image plus a logarithmic-range gain map. The format is backwards-compatible: an old viewer displays the SDR image, while a viewer that understands the metadata combines the two renditions. Adobe's gain-map documentation describes the same basic model and notes that gain maps are now standardized in ISO 21496-1.

The file I am working with is a JPEG with two images inside it: the normal SDR JPEG and an additional grayscale gain-map JPEG appended to it. The gain map says how much brighter each corresponding region can become when the display has headroom above SDR white. That is the part the AI editor throws away.

What the AI editors do

The implementation details differ between products. At the boundary, the tools I tested have the same shape: the incoming file gets decoded to pixel data, that data runs through an image model, and the result gets encoded as a new JPEG or PNG. The code that reads metadata, applies orientation, and writes the output is usually a separate image-library path. That path knows how to write pixels. It does not necessarily know that a second JPEG and a set of gain-map parameters need to survive beside them.

Neural networks like matrices, so this simplified pipeline is natural: decode the image into an RGB tensor, run a diffusion model, a segmentation-and-inpainting model, or another pixel-processing operation, then encode the output. The problem is that the gain map is not just a decorative overlay. It describes the relationship between the base pixels and their brighter rendition.

If an editor preserved the old gain map byte for byte, the map could still be wrong. The SDR pixels it was calibrated against are no longer the same pixels. Add or remove an object, change the color of a wall, or alter a local contrast boundary and the old gain map no longer lines up with the edited image. Google's Ultra HDR editing guidance makes the same distinction: simple geometric edits can transform the gain map along with the base image, but edits that change image contents may require modifying or removing it.

So the editor has two real options. It can preserve and regenerate the gain map as part of an HDR-aware pipeline, or it can return a plain SDR image. The tools I tested take the second path. If I edit a street sign out of a nature photo, the result looks flatter beside the unedited original on my iPhone or MacBook because the HDR rendition is gone.

Two metadata paths in one JPEG

This is not all of HDR, and it is not the only way to store HDR images. HEIF, AVIF, and other formats have their own ways to carry high-dynamic-range information. The AVIF specification, for example, supports HDR images and tone-map-derived image items. I am staying with JPEG here because the backward-compatible behavior is useful on the web: software that knows nothing about gain maps can still display the base image.

The JPEG I wanted had to satisfy two related metadata conventions. The first is Google's Ultra HDR path. Its XMP packet carries the gain-map parameters and a Container directory with a Primary item and a GainMap item. The GainMap item has a length, and an MPF offset table points to the second JPEG inside the file. A compatible browser can use that information to reconstruct the brighter rendition.

The second is the ISO 21496-1 gain-map path. The iPhone JPEGs I inspected carried an APP2 segment whose payload starts with urn:iso:std:iso:ts:21496:-1. In my tests, Preview.app on macOS and Photos on iOS needed those ISO markers even when the Google XMP was present. I therefore put both sets of metadata into my output rather than treating them as competing formats.

A working file carries:

  • the Google Container XMP for viewers that understand Ultra HDR;
  • ISO 21496-1 markers for the Apple path I observed;
  • the hdrgm gain-map parameters in places the readers can find them;
  • the MPF offset table linking the primary image to the gain map; and
  • an ICC profile for color handling.

All of this goes near the front of the file, before the actual image data starts. The file still opens as a JPEG when one of those pieces is missing. That is what makes these failures difficult to diagnose: a broken HDR file often looks like a working SDR file.

The file structure, for one of my actual outputs, looks like this:

PRIMARY IMAGE (~223 KB):
  SOI (start of image)
  APP0 JFIF                                 16 bytes
  APP1 XMP + Container + hdrgm           1,486 bytes   <- Ultra HDR readers need this
  APP2 MPF (offset table)                   88 bytes   <- links primary to gain map
  APP2 ISO 21496-1 marker                   34 bytes   <- Apple readers need this
  APP2 ICC_PROFILE                         604 bytes
  DQT, SOF0, DHT, SOS, image data...

GAIN MAP (~10 KB):
  SOI
  APP0 JFIF                                 16 bytes
  APP2 ICC_PROFILE                         604 bytes
  APP2 ISO 21496-1 marker + params          91 bytes   <- Apple readers need this
  APP1 XMP + hdrgm params                  616 bytes   <- redundant, also helpful
  DQT, SOF0, DHT, SOS, gain-map pixels...

Two JPEG files concatenated, with two kinds of HDR metadata woven through the
APP segments at the front of each one.

Building Ultra HDR JPEGs without libultrahdr

Google publishes libultrahdr, the reference codec for the Ultra HDR format. It is the sensible choice if you want a maintained implementation of the format. I looked at it and chose not to make it a runtime dependency for this service.

My service runs on a small CPU VPS. I wanted a narrow Python component that accepted the SDR JPEG, the gain-map JPEG, and a metadata object, then emitted the final bytes. Pulling a substantial C++ codec into that service would have meant another build and packaging surface to maintain. That is a tradeoff for this particular deployment, not a claim that libultrahdr is a bad library.

So I wrote direct_ultrahdr.py. It constructs the file by hand in about six hundred lines of Python. The pieces are:

  • Walk the primary JPEG and the gain-map JPEG to find the sequence of APP markers each one starts with.
  • Build the XMP packets as plain strings. The Container XMP for the primary image goes into an APP1 segment with the Adobe XMP identifier http://ns.adobe.com/xap/1.0/. The hdrgm XMP for the gain map goes into the same kind of APP1 segment in the gain-map JPEG.
  • Build the MPF APP2 segment. MPF is a CIPA standard with a TIFF-style header: big-endian, IFD at offset 8, and entries for the two images. The primary image lives at offset 0 with size sdr_size; the gain map lives at offset sdr_size with size gainmap_size.
  • Build the ISO 21496-1 APP2 segments. This is the one piece I did not build from the public specification. I pulled an HDR JPEG from a current iPhone, opened it in a hex editor, found the two APP2 segments whose payload started with urn:iso:std:iso:ts:21496:-1, and copied them as byte constants. The primary one is 36 bytes. The gain-map one is 93 bytes and includes gain-map parameters as packed integers.

I am not thrilled about shipping byte literals that came out of a hex dump. The specification is not freely available, while the iPhone file is a concrete sample that Preview.app accepts. For this implementation, observed device output was the ground truth.

Those constants look like this in the source:

ISO_21496_PRIMARY_APP2 = bytes.fromhex(
    "ffe2002275726e3a69736f3a7374643a69736f3a74733a32313439363a2d310000000000"
)

ISO_21496_GAINMAP_APP2 = bytes.fromhex(
    "ffe2005b75726e3a69736f3a7374643a69736f3a74733a32313439363a2d31"
    "00000000004000000000000f42400028eb29000f4240ffffe317000f424000"
    "28eb29000f4240000d5810000f42400000000a000f42400000000a000f4240"
)

The hex is the string urn:iso:std:iso:ts:21496:-1 followed by numeric fields. With those pieces, constructing the final file is mechanical: insert the APP segments into the front of the primary JPEG, before the Start of Scan marker; insert the matching segments into the gain-map JPEG; concatenate the two images; and patch the JFIF APP0 to include the four-byte AMPF marker that matches the iPhone files I inspected.

A short sanity-check function I keep around for any file anyone sends me:

def analyze_ultrahdr(path):
    with open(path, 'rb') as f:
        data = f.read()

    first_soi  = data.find(b'\xff\xd8')
    second_soi = data.find(b'\xff\xd8', first_soi + 2)
    if second_soi == -1:
        print("Not an Ultra HDR JPEG (no second image found)")
        return

    primary = data[:second_soi]
    gainmap = data[second_soi:]

    checks = {
        'MPF in primary':         b'MPF\x00' in primary,
        'Container XMP':          b'http://ns.google.com/photos/1.0/container/' in primary,
        'hdrgm namespace':        b'http://ns.adobe.com/hdr-gain-map/1.0/' in primary,
        'ISO 21496-1 (primary)':  b'urn:iso:std:iso:ts:21496:-1' in primary,
        'ISO 21496-1 (gainmap)':  b'urn:iso:std:iso:ts:21496:-1' in gainmap,
        'ICC profile':            b'ICC_PROFILE\x00' in primary,
    }
    for name, ok in checks.items():
        print(f"  {'OK ' if ok else 'NO '} {name}")

These checks do not prove that every browser or photo application will render HDR. They do tell me whether I have included the pieces that my tested Chrome and Apple viewers expect, and which part is missing when one of my outputs falls back to SDR.

Where the gain map comes from

There is a more interesting problem underneath the file format. You have an edited SDR image, the gain map is gone, and you want a new one. How do you produce it?

You cannot reconstruct the exact original gain map. The original map encoded information about scene luminance that the camera captured, and that information is gone. You can produce a plausible gain map: one that lifts the right regions on an HDR display and looks like something an HDR image pipeline could have made for the edited pixels. That is reconstruction, not recovery.

The naive version is straightforward. Compute the luminance of each SDR pixel, stretch the bright end of the range, and call that the gain map. It kind of works. Highlights lift a little and skies get more punch. But the output is generic: every sky gets the same boost, every reflection gets the same boost, and the map does not know what a face is. Apply it uniformly and skin tones get lifted along with the highlights.

My own comparisons with iPhone images suggested a more selective result: specular highlights and bright sources get the strongest lift, midtones get less, and skin and shadows are mostly left alone. That observation is about the files I tested, not a claim that every iPhone image uses the same fixed rule.

The less naive version is a neural network trained to predict a gain map from the SDR image. The one I landed on is GMNet, from the ICLR 2025 paper Learning Gain Map for Inverse Tone Mapping by Yinuo Liao, Yuanshen Guan, Ruikang Xu, Jiacheng Li, Shida Sun, and Zhiwei Xiong. The authors also released the code, checkpoints, and datasets. That made it a useful starting point: the model is explicitly trained for gain-map prediction rather than generic image enhancement.

GMNet has two branches. A global branch takes a 256×256 thumbnail of the input and extracts scene-level features. From those features it produces a small 3×3 kernel for the local branch, a channel-attention vector, and a scalar called qmax that acts as the global ceiling on the allowed boost. A local branch takes the full-resolution input through residual blocks. The branches meet when the local features are processed with the dynamically produced kernel, channel attention is applied, and the result is upsampled with pixel shuffle.

The architecture is useful because the two branches answer different questions. The global branch can see that the image is a sunset and decide that the sky should get a larger boost than the foreground. The local branch has enough resolution to paint that decision onto the correct regions. The boost kernel is produced by the network rather than fixed, so the same model can handle a noon beach shot and a candlelit dinner.

The output of the pipeline is the SDR image I uploaded, unchanged; a grayscale gain-map image derived from GMNet's prediction; and gain-map metadata containing the minimum, maximum, gamma, offsets, and display-capacity values. Those pieces go to the Ultra HDR packager, which produces a file that my tested Chrome and Apple viewers understand.

Did you notice the HDR photos?

I wanted to know how many visitors to my sites were using devices that could render the result correctly.

Browsers expose one useful signal through the dynamic-range media feature. In JavaScript, window.matchMedia('(dynamic-range: high)') reports whether the browser-display combination advertises a high dynamic range. I also record the WebGL renderer string as a rough device signal. It is not a display-capability test, but it helps explain the hardware behind a result.

In the sample I collected, about 20% of unique visitors hit dynamic-range: high. Counting events instead of visitors produced about 40% HDR-capable sessions. The sample is small and the collection path is noisy, so these are measurements of my visitors, not a market-wide estimate. The rest were on hardware that could not go brighter than SDR, on browsers without the HDR rendering path enabled, or on operating systems where the relevant support was unavailable.

The format is designed to degrade gracefully. On a capable display, the gain map can make the image visibly brighter. On everything else, the base image still works as a normal JPEG. That is useful for distribution, even though most of the audience will not see the extra range.

Upload behavior is a separate problem. Meta has publicly described HDR photo support in Instagram and Threads, but that establishes product support, not a guarantee that every upload path preserves every gain-map variant or renders it in every client. The result can depend on the platform, app version, browser, and device. The only reliable test for a specific workflow is to upload the actual file and inspect it again on the client that matters.

Where this lands

The project is a consumer photo format with a second image stitched into it, an AI editor that discards that image, a neural network that predicts a replacement, and a packager that has to satisfy more than one reader. The difficult part was not producing a plausible gain map. It was the surrounding mechanics: understanding the metadata, choosing how much of the format to implement, and checking the resulting bytes against real files from real devices.

If you edit iPhone photos through AI tools and the output looks subtly flat beside the original, the gain map may have been dropped. You can check for the hdrgm namespace, the ISO 21496-1 marker, and the second JPEG image. Reconstructing the original is impossible, but reconstructing a useful gain map is practical. Whether it is worth doing depends on where the photos are going.
